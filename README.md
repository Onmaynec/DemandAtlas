# DemandAtlas

Локальная платформа аналитики розничных продаж, прогнозирования спроса и подготовки закупок. Разработка по ТЗ PV-DATA-05 (синтетический заказчик).

В демонстрации используются только синтетические данные: 25 магазинов, 5 000 SKU и история до 24 месяцев. Реальные заказы поставщикам приложение не отправляет.

## Быстрый запуск

Необходимы Docker Engine и Docker Compose v2. Команды из корня репозитория:

    cp .env.example .env
    docker compose -f compose.yml up --build -d
    docker compose -f compose.yml exec api python -m backend.scripts.seed_demo --rows 2500 --seed 42

Откройте http://localhost:8000. OpenAPI: http://localhost:8000/docs.

### Демонстрационные роли

| Роль | Bearer-токен | Доступ |
| --- | --- | --- |
| Data engineer | demo-engineer | Источники, импорты, качество |
| Аналитик | demo-analyst | BI, модели, прогноз, черновики |
| Категорийный менеджер | demo-category | Категория Food |
| Руководитель | demo-director | BI, сценарии, утверждение |
| Наблюдатель | demo-observer | Только отчёты S001–S002 |

Вставьте токен в поле «Ключ доступа» вверху веб-интерфейса.

**Демо-токены и пароль PostgreSQL не предназначены для внешней сети и настоящих данных.** API проброшен на 127.0.0.1. Production-развёртывание требует полноценного IAM, TLS и управления секретами. См. docs/SECURITY.md.

## Демонстрационный сценарий

1. С токеном аналитика откройте «Обзор»: статистика и вклад магазинов в изменение выручки.
2. С токеном инженера в «Источниках» загрузите demo/invalid_sales.csv для demo_sales. Импорт отклоняется, причины с номерами строк доступны в журнале качества; старая витрина остаётся.
3. С токеном аналитика откройте «Прогнозирование», выберите S001 / SKU00001 и 28 дней. Backtest сравнит seasonal naive, moving average, exponential smoothing и zero baseline. Опубликуйте выбранный прогноз.
4. В «Закупках» рассчитайте сценарий, создайте план и отправьте на согласование. С токеном директора утвердите его.
5. Запросите происхождение дневной метрики через GET /api/v1/lineage с параметрами day, store, sku.

## Пример расчёта через API

    curl -X POST http://localhost:8000/api/v1/replenishment/scenario \
      -H "Authorization: Bearer demo-analyst" -H "Content-Type: application/json" \
      -d '{"storeId":"S001","sku":"SKU00001","forecastQty":35,"onHand":12,"inbound":8,"safetyStock":10,"leadDays":7,"reviewDays":0}'

Для импорта используйте POST /api/v1/pipelines/{id}/runs, передайте idempotencyKey и ровно одно поле rows либо csv. Предел: 100 000 строк на пакет и CSV до 35 МиБ.

## Тестирование

В Python 3.12:

    python -m venv .venv
    pip install -r backend/requirements.txt
    export DATABASE_URL=sqlite:///./demandatlas.db
    export DEMO_MODE=1
    export FORECAST_URL=
    pytest -q tests
    ruff check backend forecast_service tests --select E4,E7,E9,F63,F7,F82

На PostgreSQL миграции запускаются командой:

    alembic -c backend/alembic.ini upgrade head

Нагрузочная проверка (после seed):

    docker compose -f compose.yml exec api python -m backend.scripts.benchmark --rows 100000

Публиковать измерения производительности без указания железа, профиля данных и p50/p95 нельзя.

## Структура

- backend/app: FastAPI, роли, ETL raw → staging → mart, метрики, закупки;
- backend/migrations: миграция структуры БД;
- backend/scripts: синтетический seed и измеритель нагрузки;
- forecast_service: сервис четырёх baseline моделей;
- web: адаптивный интерфейс без внешних платных компонентов;
- tests: проверки расчётов, прав, качества и состояний;
- docs: архитектура, ADR, эксплуатация, приёмка.

## Статус реализации

Базовые потоки реализованы в исходниках: CSV/SQL ingestion, проверки качества, атомарный mart, idempotency, BI и CSV export, lineage, прогноз и rolling-origin, what-if, MOQ, план с версионированными переходами, серверная авторизация, Compose, CI.

**Не завершено / не подтверждено:** требуемое время обработки 100 000 строк, p95 BI, устойчивость при 3 млн строк под конкурирующей нагрузкой, полное e2e браузера и восстановление из сбоя, полный браузерный E2E, полное восстановление после сбоев и нагрузочные испытания на эталонном сервере. Полный перечень в docs/ACCEPTANCE.md.

## v0.2.0 — Data Integrity

Повторный импорт ранее опубликованного чека с тем же содержимым не увеличивает версию данных. Если количество, цена, SKU, магазин, дата или другие поля чека изменились, весь batch отклоняется с ошибкой changed_published_fact. Для подтверждённого изменения используйте безопасную замену диапазона.

Новый POST /api/v1/pipelines/{source_id}/reprocess принимает idempotencyKey, expectedDatasetVersion, start, end, storeId, reason, rows. Интервал до 31 дня, строки должны представлять ПОЛНЫЙ авторитетный срез данного источника/магазина/периода. Это операция замены, а не частичного добавления. Устаревшая версия даёт 409. Пустой список rows подтверждает отсутствие продаж за данный период. Все прежние raw-данные и опубликованные прогнозы сохраняются.

GET /api/v1/datasets/current возвращает текущую версию. GET /api/v1/metrics/coverage раскрывает конкретные пропущенные магазин-дни. В SPA добавлены форма переобработки CSV и просмотр пропущенных дней. Подробнее: docs/REPROCESSING.md и CHANGELOG.md.

Перед публичным развертыванием необходим полноценный IAM, нагрузочная проверка 3 млн строк и устойчивое восстановление после сбоя — v0.2.0 этих требований полностью не закрывает.


## v0.3.0 — Retail Intelligence

Добавлены «Анализ KPI» и «Риски запасов» в левом меню. Новый анализ разлагает изменение выручки, количества и маржи между двумя равными последовательными периодами по магазину/региону/категории/SKU, показывает арифметический вклад и охват данных. Через выбор строки можно спуститься до SKU, сохраняя период, магазин и категорию. **Вклад не означает причинно-следственный эффект**.

Оценка дефицита/излишков строится из опубликованных продаж и инвентаря: история 7–90 дней, срок поставки, интервал пересмотра, максимальное покрытие запасов. Недостаточный охват магазин-дней возвращает статус insufficient_data вместо точной оценки спроса. Важно: inbound учтён без дат поставки, показатели ориентировочные, а не вероятность потерь или заказ поставщику.

Экспорт: GET /api/v1/reports/sales.xlsx и CSV с одинаковыми серверными фильтрами (start, end, store, region, category, sku), до 10 000 SKU. XLSX содержит метаданные версии набора, охват, формулы KPI, таблицу SKU и числовые итоги. Выгрузки доступны только analyst, category_manager, director; область видимости enforced на сервере. Неавторизованные пользователи не могут выгрузить скрытые категории или магазины. Значения, похожие на Excel-формулы, сохраняются как текст.

Новые API: GET /api/v1/insights/contributions, GET /api/v1/replenishment/risks. См. docs/RETAIL_INTELLIGENCE.md, CHANGELOG.md и docs/releases/v0.3.0.md.


## v0.4.0 — Security & Reliability

Добавлены локальные identity и access-keys в PostgreSQL, настройка role/store/category scope, отзыв и ротация высокоэнтропийных токенов и отдельный администратор access_admin без прав бизнес-отчётности. Создание первого администратора:

    docker compose exec api python -m backend.scripts.manage_access bootstrap --name operator

Сохраните сгенерированный ключ: он показывается только один раз. Следующие пользователи создаются через вкладку «Управление доступом» или API. В браузере нет предзаполненного ключа: в локальном демо введите demo-analyst; для production введите выданный ключ.

Для managed-only режима задайте APP_ENV=production, DEMO_MODE=0, удалите все TOKEN_* из .env и замените FORECAST_SERVICE_TOKEN; убедитесь, что пароль PostgreSQL в .env и compose.yml не является демо. Приложение отказоустойчиво запрещает запуск в production с демо-ключами; это не заменяет TLS и полноценный deployment hardening.

В v0.4.0 добавлен журнал изменяющих запросов с актором/requestId (без тел и токенов), общий rate limit на уровне базы и ограничение размера запросов. Проверены серверные запреты доступа к данным через другие роли и ревокация ключей. Документация: docs/SECURITY.md и docs/releases/v0.4.0.md.

Ограничения: дополнительные browser E2E, нагрузочная аттестация, fault injection и атомарный аудит всех бизнес-операций ещё не завершены.
