# Переобработка продаж — v0.2.0

Операция предназначена для data_engineer. При обычной загрузке идентичность продажи равна sourceId + transactionId + lineId. Точный повтор не изменяет данные; изменение уже опубликованного чека отклоняется и журналируется.

## Контракт и порядок

1. Получить GET /api/v1/datasets/current с Bearer-токеном инженера.
2. Подготовить ПОЛНЫЙ авторитетный CSV за один магазин и 1–31 последовательный день.
3. Вызвать POST /api/v1/pipelines/{source_id}/reprocess.
4. Проверить статус и findings: GET /api/v1/quality/runs/{runId}.

Пример тела:

    {
      "idempotencyKey": "verified-s001-20261101-01",
      "expectedDatasetVersion": 17,
      "start": "2026-11-01",
      "end": "2026-11-01",
      "storeId": "S001",
      "reason": "Сверка кассового отчёта и расхождений по смене",
      "rows": [{
        "date": "2026-11-01",
        "store_id": "S001",
        "sku": "SKU00001",
        "transaction_id": "TX-123",
        "line_id": "1",
        "qty": 3,
        "unit_price": "120.00",
        "unit_cost": "70.00"
      }]
    }

Это SNAPSHOT-замена: не указанные в rows продажи этого источника, магазина и диапазона удаляются из текущего staging. Другие источники/магазины не затрагиваются. Если rows пуст, это подтверждение нулевых продаж. Система пересчитывает затронутые агрегаты из всех источников и отмечает подтверждённые дни в coverage.

Повтор с тем же idempotencyKey и телом возвращает существующий run. Повтор с другим телом даёт 409. Устаревшая expectedDatasetVersion даёт 409 до изменений. Критические findings приводят к статусу rejected, витрина остаётся прежней. Исходные raw-факты старых и новых запусков сохраняются.

При переобработке берётся блокировка dataset_state, проверяется существование внешних идентичностей за пределами среза, пересчитываются touched date/store/SKU и удаляются пустые агрегаты. Публикуемые прогнозы/утверждённые планы не переписываются.

## Ограничения и восстановление

Операция синхронная и допускает не более 100 000 строк за запрос; требуется планирование длительных загрузок. Для реального SLA необходимы PostgreSQL fault injection, 3 млн строк, тесты рестарта процессов, durable очередь и управление полномочиями без демо-токенов. Не отправляйте частичный список исправлений, иначе исчезнут все не перечисленные в snapshot чеки указанного среза.
