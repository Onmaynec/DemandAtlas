# Архитектура DemandAtlas

## Поток данных

CSV или тестовая SQL таблица → pipeline_runs и raw_sales/raw_stocks → quality_findings → staged_sales → daily_sales_mart в PostgreSQL. Публикация staging, inventory, mart, coverage и dataset_version происходит одной транзакцией. Критическое нарушение блокирует транзакцию, но raw и findings остаются.

## Сущности и ключи

- stores.id, products.sku — стабильные идентификаторы.
- pipeline_runs: уникальный (source_id, idempotency_key), checksum SHA-256.
- staged_sales: составной PK (source_id, transaction_id, line_id).
- daily_sales_mart: уникальный (date, store_id, sku), агрегаты units, revenue, cost.
- daily_coverage: уникальный (date, store_id), используется в отчётах неполноты.
- forecasts: неизменяемая версия прогноза, dataset_version, model_version, seed, parameters.
- plans: текущий статус и version; plan_revisions: журнал переходов.
- inventory: on_hand/inbound на магазин и SKU.

Временные метки операций фиксируются в UTC; бизнес-даты продаж в CSV передаются без часового пояса и должны нормализовываться при интеграции источника по календарю магазина. Индексы по датам, магазинам и SKU.

## Контроль качества

Правила: null первичных ключей, дубликаты строк чека, отрицательный qty, неизвестный SKU/магазин, неверный формат даты/цены, разрывы по дням. Предупреждения о днях не блокируют публикацию; критические нарушения отменяют её. Повтор batch с тем же ключом и checksum возвращает прежний run, другая нагрузка с тем же ключом получает конфликт. Составной ключ не позволяет удвоить транзакцию при повторе.

## Метрики и формулы

Выручка = Σ(qty × unit_price). Единицы = Σqty. Маржа = Σ(qty × (unit_price − unit_cost)). WAPE = Σ|прогноз − факт| / Σфакт; при Σфакт=0 не определена. Bias = средняя величина (прогноз − факт).

Рекомендуемый заказ = max(0, прогноз + safety stock − on_hand − confirmed inbound), затем применяется MOQ и округление к кратности упаковки; при нулевой потребности заказ равен нулю.

## Прогнозирование

Отдельный Python сервис: seasonal naive (период 7), moving average (окно 7), exponential smoothing (alpha 0.3) и zero baseline. Rolling origins с min_train=28, все кандидаты проходят общие test folds. Дальнейшие точки строятся из истории на момент публикации, а модель/параметры/seed сохраняются с dataset_version.

## Доступ

Демо-профили — инженер, аналитик, категорийный менеджер, директор, наблюдатель. API фильтрует по scope магазинов/категорий, включая сравнения, экспорт, lineage, прогноз и планы. UI не заменяет серверных запретов. Продакшен-управление учётными записями вынесено в backlog.

## Текущие ограничения

- Ограничение 2000 строк группированных BI-запросов. Для крупных наборов нужна cursor pagination.
- Импорт синхронный; нужна durable очередь с retries и автоматической переобработкой исправленных фактов.
- SQL-коннектор читает только простое имя таблицы в тестовой БД; произвольные выражения запрещены.
- Пропуски дней могут обрабатываться как нули прогноза, но всегда маркируются в historyQuality.
- Требования 100 000 / 5 минут и BI p95 ≤ 2 секунд нуждаются в измерениях на эталонном оборудовании.
